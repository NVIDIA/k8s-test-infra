# Observability demo — Prometheus + Grafana over mock GPUs

This demo runs a **real** monitoring stack — kube-prometheus-stack and NVIDIA's
own `dcgm-exporter` — against a Kind cluster with **no physical GPUs**, then
injects GPU faults and proves they land in the recorded time series. The GPUs are
simulated by `nvml-mock` at the driver level, so `dcgm-exporter` is unmodified and
unaware.

Faults are injected into a *running* exporter, so the dashboard shows a **step
change** in a continuous series rather than a gap. Every phase is asserted against
Prometheus and the script exits non-zero if an injected fault never arrives, so it
doubles as a regression check on the whole scrape path.

Addresses [#597](https://github.com/NVIDIA/k8s-test-infra/issues/597).

> **Treat this cluster as throwaway.** The Grafana and Prometheus ports are
> published on `0.0.0.0`, so anyone on your local network can reach Grafana with
> the demo's default password (`mokka`) and an entirely unauthenticated
> Prometheus. Do not run it on an untrusted network.

## Requirements

- Docker, [Kind](https://kind.sigs.k8s.io/), Helm, `kubectl`, `jq` (all required —
  the script preflights them)
- **bash 4 or newer**, not preflighted: `run.sh` uses `mapfile`, so a host whose
  `bash` is the stock macOS 3.2 aborts at the worker-discovery step.
- **Host ports 3000 and 9090 must be free.** There is no preflight for them; a
  local dev server on 3000 makes `kind create cluster` fail with an opaque Docker
  port-allocation error.
- Network access to `nvidia.github.io` (container-toolkit packages),
  `prometheus-community.github.io` and `helm.ngc.nvidia.com` (charts), plus the
  registries those charts pull from.

## Run it

```bash
cd docs/demo/observability
./run.sh
```

A first run from scratch takes roughly **10–15 minutes**, dominated by the
`nvml-mock` image build and waiting for the GPU Operator to settle (one measured
rebuild: 10m46s). The script is idempotent and reuses the cluster, so a warm
re-run — which still clears the old overrides and re-proves both faults —
finishes in **under two minutes**. Set `FORCE_RECREATE=true` to rebuild the
cluster.

## What the script does

1. **Cluster** — creates the Kind cluster from [`kind.yaml`](kind.yaml) (1
   control-plane + 2 workers, CDI enabled in containerd, Grafana and Prometheus
   NodePorts mapped to the host), labels both workers `nvml-mock-gpu=true`, and
   installs `nvidia-container-toolkit` in CDI mode into each worker.
2. **Mock GPUs** — builds and loads the `nvml-mock` image, then installs the chart
   onto the workers with `dynamicMetrics` enabled. Without dynamic metrics every
   panel is a flat line.
3. **kube-prometheus-stack** — installed with
   [`kube-prometheus-stack-values.yaml`](kube-prometheus-stack-values.yaml)
   **before** the GPU Operator, so the `ServiceMonitor` CRD exists by the time the
   operator creates one.
4. **GPU Operator** — installed with
   [`gpu-operator-values.yaml`](gpu-operator-values.yaml): real driver and toolkit
   disabled (the mock provides them), `dcgm-exporter` and its `ServiceMonitor`
   enabled. The script then asserts the exporter target is actually **up** in
   Prometheus and that the DCGM series are present.
5. **Dashboard** — provisions [`dashboards/mokka-gpu.json`](dashboards/mokka-gpu.json)
   through a ConfigMap labelled `grafana_dashboard=1`, then asserts Grafana's own
   search API reports it imported.
6. **Phase 1 — heat** — clears any leftover override, records the baseline, pins
   gpu 0 on the first worker to `HOT_TEMP_C`, and waits for that exact value in
   Prometheus. It also asserts the sibling GPUs kept their own readings, so a pin
   that leaked across the node cannot pass.
7. **Phase 2 — fault** — injects an `ecc_uncorrectable` failure with an Xid and
   waits for `DCGM_FI_DEV_XID_ERRORS` to carry that code.
8. **Continuity** — compares pod names and restart counts before and after
   injection, and fails if anything was recycled.

## The pipeline

```
nvml-mock DaemonSet          stages a fake driver root on each node
        ▼
dcgm-exporter (real NVIDIA)  loads the mock libnvidia-ml.so, serves :9400
        ▼
ServiceMonitor               generated by the GPU Operator, release-labelled
        ▼
Prometheus  ──►  Grafana     dashboard provisioned from a ConfigMap
```

Faults are injected with `nvml-mock-ctl`, not with `helm upgrade`. A Helm upgrade
recycles the exporter pod and breaks the series; the CLI writes a node-local
overlay that the running exporter picks up within the mock engine's TTL, so the
timeline stays continuous.

## Access

| Service | URL | Credentials |
|---------|-----|-------------|
| Grafana | <http://localhost:3000/d/mokka-gpu> | `admin` / `mokka` (`GRAFANA_PASSWORD`) |
| Prometheus | <http://localhost:9090> | none |

Those host ports exist **only** so a human can open a browser. The script's own
assertions query Prometheus through the API-server *service* proxy — mirroring how
the repo's Go E2E suite scrapes `dcgm-exporter` through the API-server *pod* proxy
— so they do not depend on the host port mapping at all.

## Dashboard panels

| Panel | Query | Reading it |
|-------|-------|-----------|
| GPU temperature | `DCGM_FI_DEV_GPU_TEMP` | One line steps up and goes flat where the heat was injected |
| Last Xid code reported | `DCGM_FI_DEV_XID_ERRORS` | The **code** of the most recent Xid, not a count |
| Power draw | `DCGM_FI_DEV_POWER_USAGE` | Clock-driven simulation, not real work |
| GPU utilization | `DCGM_FI_DEV_GPU_UTIL` | Clock-driven simulation, not real work |
| GPU inventory — advertised vs requested | `kube_node_status_capacity` vs `kube_pod_container_resource_requests` | Advertised capacity against what workloads request |
| Component health — ready vs desired, and restarts | `kube_daemonset_status_*`, `kube_pod_container_status_restarts_total` | Ready below desired, or a climbing restart count, is the signal. Restarts are **per pod** and scoped to `nvml-mock` and `dcgm-exporter`: a per-namespace sum buries a Mokka pod inside the GPU Operator's own operand churn, which runs into the dozens on a healthy cluster |

**Read these with the right expectations.** The mock never executes a kernel, so
every value is configuration, a clock-driven simulation, or a fixed derivation —
see [Metric Fidelity](../../configuration.md#metric-fidelity) for which is which.

Two things about the Xid panel routinely look like bugs and are not:

- **It is empty until a fault fires.** `DCGM_FI_DEV_XID_ERRORS` has *no series at
  all* on a healthy cluster: the mock delivers Xids through the NVML event set, and
  `dcgm-exporter` omits field 230 entirely while it holds no value for it. The
  panel reads *"no Xid reported yet"* until phase 2 injects one.
- **The injected code alternates between consecutive runs** — 79, then 48, then 79
  again. DCGM latches the last Xid per device and never retracts it, so injecting
  the same code twice would let the assertion pass on the previous run's residue.
  Rotating between two codes guarantees every run witnesses a genuinely fresh
  delivery. A diff of two runs' logs, or a changing legend value, is the design
  working.

## Configuration

Overridable via the environment:

| Variable | Default | Purpose |
|----------|---------|---------|
| `CLUSTER_NAME` | `nvml-mock-observability` | Kind cluster name |
| `FORCE_RECREATE` | `false` | Delete and rebuild the cluster first |
| `KIND_NODE_IMAGE` | `kindest/node:v1.35.0` | Kind node image |
| `IMAGE_REPO` | `nvml-mock` | Mock image repository |
| `IMAGE_TAG` | `observability-demo` | Mock image tag |
| `GPU_PROFILE` | `h100` | Mock GPU profile; Hopper+ so the `DCGM_FI_PROF_*` fields populate |
| `GPU_COUNT` | `8` | Mock GPUs per worker; **minimum 2** — phase 1's scope check needs a sibling GPU to compare against and fails outright with none |
| `TARGET_GPU` | `0` | GPU the faults are injected into |
| `HOT_TEMP_C` | `90` | Temperature pinned in phase 1; **capped at 92 on `h100`**, see below |
| `XID_CODE` / `XID_CODE_ALT` | `79` / `48` | The two codes phase 2 rotates between; must differ |
| `MONITORING_NAMESPACE` | `monitoring` | Namespace for kube-prometheus-stack |
| `KPS_RELEASE` | `monitoring` | kube-prometheus-stack release name |
| `KPS_VERSION` | `88.3.0` | Chart version |
| `GPU_OPERATOR_VERSION` | `v26.3.3` | GPU Operator version |
| `GRAFANA_PASSWORD` | `mokka` | Grafana admin password |
| `FAULT_POLL_ATTEMPTS` / `FAULT_POLL_INTERVAL_S` | `36` / `5` | Budget for each "did it reach Prometheus?" poll |

`IMAGE_REPO` and `IMAGE_TAG` are the image knobs; the full reference is derived
from them, so exporting `IMAGE_NAME` has no effect.

**`HOT_TEMP_C` is clamped to the profile's thermal shutdown threshold — 92 °C on
`h100`.** `nvml-mock-ctl temp` always writes a `dynamic_metrics.temperature` block
and the device rebuilds its simulator from it, so the clamp applies whether or not
the profile enables dynamic metrics. Values up to and including 92 read back
verbatim; anything above reads back as 92. Phase 1 waits for the *exact* value it
pinned, so `HOT_TEMP_C=95` spends the full 180 s poll budget
(`FAULT_POLL_ATTEMPTS` × `FAULT_POLL_INTERVAL_S`) and then fails with
`never became == 95` — a message that never mentions clamping.

**`MOKKA_NAMESPACE` (`mokka`) and `GPU_OPERATOR_NAMESPACE` (`gpu-operator`) are
deliberately not overridable.** `dashboards/mokka-gpu.json` pins both names in
every query of the component-health panel, and a dashboard is static JSON, so an
override would install and import cleanly while silently emptying that panel. The
two must move together.

`KPS_RELEASE` is also the release label put on the `dcgm-exporter`
`ServiceMonitor` (via `--set`, not hardcoded in `gpu-operator-values.yaml`).
kube-prometheus-stack only selects `ServiceMonitor` objects carrying its own
release label and ignores the rest **silently** — no error, just a missing target.
That is the most common way to break this demo, which is why `run.sh` asserts the
target is up instead of assuming it.

## Injecting faults by hand

Each change takes **25–45 seconds** to appear (mock override TTL + exporter
collect interval + scrape interval), so **run the injections one at a time and
give each one up to a minute** before moving on. Pasted as one block they all
land inside a single scrape interval and no panel ever renders the intermediate
state.

First, find the mock pod on the node you want to fault:

```bash
CTX=kind-nvml-mock-observability
NODE=nvml-mock-observability-worker
MOCK=$(kubectl --context $CTX -n mokka get pod -l app.kubernetes.io/name=nvml-mock \
  --field-selector spec.nodeName=$NODE -o jsonpath='{.items[0].metadata.name}')
```

Heat gpu 0, then wait and watch "GPU temperature" step up and go flat (90 is
under the clamp described in [Configuration](#configuration)):

```bash
kubectl --context $CTX -n mokka exec "$MOCK" -- nvml-mock-ctl temp --gpu 0 90
```

Then raise an Xid on the same GPU and wait again for "Last Xid code reported".
DCGM latches the last code per device and never retracts it, so pick one the
panel is not already showing — the run's own closing summary prints the code to
use next:

```bash
XID=48   # or whichever code the summary offered
kubectl --context $CTX -n mokka exec "$MOCK" -- nvml-mock-ctl fail --gpu 0 \
  --mode ecc_uncorrectable --after-calls 1 --xid $XID
```

`reset` **undoes both of the above** — it drops the whole override for that GPU —
so run it only once you have seen the two steps land:

```bash
kubectl --context $CTX -n mokka exec "$MOCK" -- nvml-mock-ctl reset --gpu 0
```

The temperature returns to a simulator-driven reading, but the Xid panel keeps
showing the latched code until a different one is injected.

See [`nvml-mock-ctl`](../../nvml-mock-ctl.md) for the full command set.

## Footprint

Issue #597 requires this be sized against the per-node budget:

- Alertmanager disabled, and the bundled Kubernetes alert rules are not created
  (they fire constantly on Kind).
- Prometheus retention capped at 2h with explicit resource limits.
- `node-exporter` stays enabled — host CPU and memory pressure is what a scale run
  needs to correlate GPU symptoms against. It is the one **per-node** DaemonSet
  this stack adds.
- kube-state-metrics is a single Deployment, not per-node.

## Troubleshooting

- **`connection refused` on every `kubectl`, cluster looks up.** The script
  re-exports the kubeconfig only when the context is missing *entirely*, so an
  entry left pointing at a recreated cluster's old API-server port is not
  auto-healed. Fix it with `kind export kubeconfig --name nvml-mock-observability`,
  or run with `FORCE_RECREATE=true`.
- **`kind create cluster` fails allocating a port.** Free host ports 3000 and 9090.
- **Prometheus never scrapes `dcgm-exporter`.** Check the `ServiceMonitor` carries
  `release=<KPS_RELEASE>`; the script prints it on failure. Note the operator's own
  `gpu-operator` `ServiceMonitor` legitimately lacks that label and is ignored.
- **Pods recycled during injection.** The GPU Operator can replace its operands a
  reconcile period after `nvml-mock` rolls
  ([#602](https://github.com/NVIDIA/k8s-test-infra/issues/602)). Re-running
  converges.

## Not covered

- Mokka's own binaries still expose no `/metrics`; `mokka-control-plane` and the
  NRI plugin serve only `/healthz` and `/readyz`. Component-level instrumentation
  is the remaining half of
  [#597](https://github.com/NVIDIA/k8s-test-infra/issues/597).
- Retaining the series as a CI artifact is
  [#252](https://github.com/NVIDIA/k8s-test-infra/issues/252).
- No Tilt integration and no alerting rules.
